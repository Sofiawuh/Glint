# 个人翻译工具简化链路设计规格

> 状态：待用户书面审阅
> 关联任务：取消普通翻译与手动 GPT 处理中的阻断性格式、事实和占位符校验
> 影响架构：`docs/architecture/overview.md` 中的智能翻译工作台、Translator 与 GPT 数据流

## 1. 产品定位

Glint 是用户个人使用的翻译工具，不是审计、合规或内容防篡改系统。翻译链路优先保证简单、稳定和结果可见，不再为了保护数字、日期、实体、列表顺序或结构化样式而拒绝服务已经返回的文本。

本次改造将翻译和 AI 处理明确分为两条互不依赖的直线：

```text
选中文字 → Azure Translator → 直接显示译文

用户主动点击排版或润色 → Azure GPT → 直接显示 GPT 返回文本
```

## 2. 普通翻译

- 用户点击“翻译”或“重新翻译”时，只调用 Azure Text Translation。
- 不调用 Azure GPT，不执行 GPT 输出解析，也不执行 AI 内容校验。
- Translator 返回成功状态和非空译文后立即显示。
- 不再把数字、日期、金额、百分比、URL、邮箱、IP、文件路径、变量名或其他内容替换为内部占位符。
- 不再要求 Azure 原样返回占位符，不再因为字符、实体、数字、列表数量或顺序发生变化而拒绝整篇译文。
- 不再使用逐行、表格单元格或区块类型解析作为普通翻译成功的前置条件。
- 正常长度文本作为一个请求直接发送；超过 Azure 单次字符预算时，只按长度拆分，并优先在空行或换行处切分，结果按原顺序拼接。
- Translator 返回的换行和文字按原样进入译文编辑区；应用不再二次判断翻译内容是否“忠实”。

普通翻译只有以下情况可以失败：

- Endpoint、Key、Region 或目标语言配置无效；
- 网络错误、超时或 Azure 返回非 2xx；
- Azure 响应中没有任何非空译文；
- 用户取消或更晚的请求已取代当前请求。

Translator 错误必须明确写“Azure Translator”，不得再显示成 Azure GPT 错误。

## 3. 手动排版与润色

- Azure GPT 只在用户主动点击以下动作时调用：
  - 原文“排版”或“润色”；
  - 译文“排版”或“润色”；
  - 底部“一键智能排版”或“一键智能润色”。
- GPT 请求和响应都使用普通文本，不再要求 JSON、`source_blocks`、`translation_blocks`、区块类型或其他结构协议。
- 排版提示词要求返回处理后的完整文本，只调整段落、换行、标题、列表和阅读层级。
- 润色提示词要求返回润色后的完整文本，可以改进语法、措辞、语气和可读性。
- 应用不再执行逐字符一致、命名实体、数字、日期、金额、URL、列表数量、列表顺序或事实 token 校验。
- 只要 GPT 返回非空文本，就采用该文本。
- 原文和译文单侧处理各发送一个普通文本请求。
- “一键”处理不再要求 GPT 在一个 JSON 中同时返回两侧；改为对原文和译文分别发起普通文本请求。
- 一键处理时两侧相互独立：一侧成功就更新该侧，另一侧失败则保留该侧原内容，不回滚已经成功的一侧。

## 4. 展示与编辑

- 保留当前原文、译文双编辑区、复制、朗读、重新翻译、最近结果和自适应窗口。
- 原文和译文仍然可以自由编辑。
- GPT 返回文本直接显示在对应编辑区，不经过结构化区块渲染器。
- 标题、列表和段落的视觉层级由 GPT 返回的普通文本换行与符号表达，不再依赖模型返回区块类型。
- 顶部复制全部、单侧复制和 RTF 复制继续使用编辑区当前内容。
- 底部模式选择只决定下一次手动 AI 动作使用“排版”还是“润色”，不影响普通 Translator 请求。
- 普通翻译完成后的状态固定为“翻译完成”；不得因为当前模式显示为“智能排版”而自动调用 GPT。

## 5. 失败处理

### 5.1 Translator

- Translator 真实失败时保留原文和已有译文。
- 使用红色、准确的 Translator 错误提示。
- 不得使用 GPT 相关错误文案。

### 5.2 GPT

- GPT 网络、配置、空响应或服务端失败时保留处理前文本。
- 使用普通中性色提示，例如“智能处理未完成，当前内容未改变”。
- GPT 失败不是翻译失败，不显示大段红色警告，不清空译文，不影响复制、朗读和重新翻译。
- 不再出现“返回内容不完整或格式异常”“可能改动受保护内容”等限制性错误。

## 6. 删除或退出主链路的能力

以下能力不再参与生产翻译与 AI 处理：

- `TranslationProtectedToken` 及 Translator 占位符注入和逐个恢复；
- `TranslationContentValidator` 的字符忠实和受保护事实校验；
- GPT `source_blocks` / `translation_blocks` / `blocks` JSON 协议；
- GPT 区块类型白名单与区块数量、类型对应要求；
- AI 结果通过 `TranslationBlockRenderer` 后才能采用的限制；
- Translator 与 GPT 共用 `invalidResponse` 错误含义。

旧类型如果仍被其他测试或历史代码引用，可以暂时保留，但不得继续位于普通翻译或手动 GPT 的运行主链路中。后续在确认无引用后再安全删除，不为本次改造增加额外迁移复杂度。

## 7. 测试设计

业务契约由全新上下文的独立测试 Agent 先编写并确认旧实现红灯，再修改生产代码。

- 普通翻译在智能排版或智能润色模式下也只调用 Translator，不调用 GPT。
- 含数字、日期、金额、URL、邮箱、路径和列表的文本可以直接获得译文，不经过占位符硬校验。
- Translator 返回非空译文即成功，错误文案不会提到 GPT。
- 单侧 GPT 返回任意非空普通文本时直接采用，不要求 JSON。
- 一键 GPT 对两侧分别处理；单侧失败不影响另一侧成功结果。
- GPT 空响应或网络失败保留原内容，并显示中性提示。
- 普通翻译、重新翻译、复制、朗读、最近结果和自适应布局回归通过。
- `arm64`、`x86_64` 类型检查、Universal 构建、固定签名安装和隔离 UI smoke 通过。

所有测试只使用虚构文本，不读取或记录真实选区、邮件、剪贴板、API Key 或 Keychain 内容。

## 8. 验收标准

- 选中文字点击翻译后，只要 Azure Translator 成功返回非空文字，译文一定显示。
- 普通翻译不会调用 GPT，也不会出现 GPT 格式或内容保护错误。
- 数字、日期、实体、URL、列表或格式变化不会导致整篇翻译被拒绝。
- 只有用户主动点击排版或润色才调用 GPT。
- GPT 返回普通文本即可应用，不要求 JSON 或结构化区块。
- GPT 失败时原文和译文保持不变，普通翻译结果继续可用。
- 用户界面不再出现与个人翻译工具无关的审计级限制提示。
