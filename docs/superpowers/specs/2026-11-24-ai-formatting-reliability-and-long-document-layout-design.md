# Glint 智能排版可靠性与长文工作台设计

日期：2026-11-24
状态：已实施
影响模块：Azure GPT 结构化排版、内容保护、翻译工作台布局

## 1. 背景与目标

当前智能排版存在两类用户可见失败：模型响应已包含可用内容，但因返回外壳或原译文区块结构不完全一致而被判定为“解析失败”；模型将普通请求识别为重点区块后，原生渲染器补入项目符号，随后又被字符忠实校验判定为“改动受保护内容”。长邮件工作台同时受最低窗口高度和上下等高约束影响，正文可视区域过浅。

本次目标是：

- 提高 Azure GPT 结构化响应在真实邮件场景中的可解析性；
- 保留严格的事实与字符安全边界，不让失败的 GPT 后处理覆盖 Translator 成功结果；
- 允许原文和译文拥有各自合理的区块结构；
- 让智能排版的视觉强调不改变可复制的正文字符；
- 提升长文初始阅读空间，同时保持短文窗口紧凑和用户可调整能力。

本次不改变 Azure-only 产品边界，不恢复其他模型供应商，不把智能排版改为自动触发，也不读取、记录或上传用户凭据之外的额外数据。

## 2. 结构化响应边界

### 2.1 请求

继续使用 Azure OpenAI `/openai/v1/chat/completions`，一次请求同时提交原文和译文。提示词继续要求只返回 `source_blocks` 与 `translation_blocks`，并限制区块类型为：

- `salutation`
- `heading`
- `paragraph`
- `key_points`
- `quote`
- `code`
- `table`
- `signature`

模型不得决定颜色、字体、字号、HTML、CSS 或其他视觉参数。视觉由 Glint 原生组件统一渲染。

### 2.2 容错 JSON 提取

解析器接受以下等价外壳：

- 纯 JSON 对象；
- `json` 或普通 Markdown 代码围栏中的 JSON；
- JSON 前后带有简短自然语言说明；
- JSON 字符串中包含转义引号、括号或换行。

实现必须以字符串状态感知的括号配对方式提取第一个完整顶层 JSON 对象，不能使用简单的首尾截断或贪婪正则。提取后仍执行严格 JSON 反序列化。

顶层仍只接受规定的两个数组；区块仍只接受规定字段。未知区块类型以及颜色、字号、HTML 等额外视觉字段继续拒绝，避免模型影响原生视觉和安全边界。

### 2.3 原译文结构独立

`source_blocks` 与 `translation_blocks` 分别校验为非空、合法的区块数组，不再要求：

- 区块总数相同；
- 对应位置区块类型相同；
- 重点列表项目数相同。

原因是翻译后的自然段、问候语和签名边界可能与原文不同，而当前界面也没有逐行对齐的展示契约。两侧分别通过内容保护后即可采用各自结构。

## 3. 无损渲染与内容保护

### 3.1 智能排版

智能排版允许调整 Unicode 空白、换行和区块结构，但所有非空白字符及其顺序必须保留。

`key_points` 的强调通过原生段落缩进、背景、边线和字重实现。若模型返回的项目文本原本没有列表标记，渲染器不得自动写入 `•`、编号或其他正文字符；若原文已有列表标记，则原样保留。

因此屏幕显示、纯文本复制和 RTF 复制中的正文字符保持一致，视觉样式仅存在于富文本属性中。

### 3.2 智能润色

智能润色继续允许改善译文措辞，但必须保留：

- 人名、组织和资源名称；
- 工单号、标识符和代码 token；
- 金额、百分比、日期、时间和数字；
- URL、邮箱、IP、路径和变量；
- 列表事实数量与顺序。

原文侧仍按智能排版的无损规则处理。

### 3.3 失败保护

任一批次出现以下情况时，不覆盖当前原文或 Translator 译文：

- HTTP 或网络错误；
- 无法提取完整 JSON；
- JSON 或区块结构非法；
- 智能排版字符忠实校验失败；
- 智能润色事实保护校验失败；
- 请求被取消或已被更新的请求代次取代。

UI 错误信息区分“返回内容不完整或格式异常”与“内容安全检查未通过”。日志只记录错误类别和请求生命周期，不记录正文或 API Key。

## 4. 长文工作台布局

### 4.1 高度策略

沿用现有分类阈值：原文或译文最长一侧不超过 1,600 个字符、且任一侧最多 14 行时视为短文本；超过任一阈值即视为长文本。短文本继续采用约 430pt 的紧凑高度。长文本打开时：

- 优先使用 760pt 初始高度；
- 不超过当前屏幕可用高度减去 24pt 安全边距；
- 小屏幕上使用可用高度范围内的最大安全值；
- 用户主动调整后的窗口尺寸仍可保存，但保存值不能把长文初始窗口压回现有的浅条形状态。

### 4.2 正文区域

原文与译文继续为两个独立卡片和两个独立垂直滚动区。正常屏幕空间下，每个正文滚动区的初始可视高度至少为 240pt；当屏幕确实不足时允许约束降级，由两个滚动区共享剩余空间，不产生越界或水平滚动。

上下卡片继续等高，保证比较关系稳定；本次不增加拖拽分隔条，避免引入额外状态和交互复杂度。

正文保留现有字号、行距、编辑、朗读、单侧复制、右上角复制全部、图钉和关闭行为。

## 5. 测试与验收

使用完全虚构的长邮件样本，不使用用户截图中的真实正文或标识符。

### 5.1 AI 协议契约

- 可解析纯 JSON、代码围栏 JSON、带前后说明的 JSON；
- JSON 字符串内的括号与转义引号不破坏对象提取；
- 原文和译文区块数量或类型不同仍可分别解析；
- 未知区块类型、视觉参数和非法字段仍被拒绝；
- 缺失任一侧或空区块仍被拒绝。

### 5.2 内容保护契约

- 普通请求句被识别为 `key_points` 时，渲染结果不新增项目符号且通过智能排版校验；
- 已有项目符号保持不变；
- 工单号、金额、日期、URL、邮箱和占位名称的改动继续被拒绝；
- GPT 失败时保留处理前原文和 Translator 译文。

### 5.3 布局契约

- 短内容继续收紧到紧凑高度；
- 长内容采用不低于既定长文高度目标的工作台；
- 正常 900×760 工作台中两个正文滚动区均达到至少 240pt；
- 两侧保持独立垂直滚动；
- 小屏幕约束下不越出可用屏幕。

### 5.4 发布验收

- 运行相关 Swift 契约测试与完整仓库测试；
- 构建 `arm64 + x86_64` Universal App 和 DMG；
- 使用 `Glint Self Signed` 签名并验证 Bundle ID `com.yoryon.glint`；
- 安全备份并替换 `/Applications/Glint.app`，重启后确认进程、签名、架构和核心 UI；
- 推送功能分支，创建 PR，以 merge commit 合并 `main`，不 squash、不 rebase，并保留功能分支。

## 6. 非目标

- 不让模型直接返回 Markdown、HTML 或自由视觉样式；
- 不为原文和译文分别发起两次常规 GPT 请求；
- 不关闭或弱化事实保护；
- 不自动执行智能排版或智能润色；
- 不改变 Azure Translator、Azure Speech、Keychain 和快捷键体系；
- 不新增持久化邮件正文或 AI 响应日志。
