# Glint AI 智能排版、智能润色与 Speech 设置设计

日期：2026-11-24  
状态：已批准并实施

## 1. 目标

本版本解决两个已经复现的问题：

1. 现有本地规则无法稳定恢复邮件、网页、PDF 和长文本中的真实段落、列表与签名，导致 `customer.In addition`、`2141.It appears`、项目符号挤在同一段等排版错误；
2. Azure Speech 当前要求用户填写完整 TTS Endpoint 和自由文本 Voice，容易把 Azure Portal 的通用终结点填入 Endpoint、把 Region 填入 Voice，并且失败提示无法指出真正错误字段。

版本新增两个相互独立的 Azure GPT 能力：

- **智能排版**：只恢复文本结构，不改变文字内容；
- **智能润色**：在保留事实信息的前提下改善语法、用词、语气和可读性。

同时将 Speech 设置简化为 Endpoint 和 API Key 两项；Glint 自动识别区域、生成实际 TTS REST 地址并按文本语言选择声音。

## 2. 用户界面与默认行为

### 2.1 基础设置

基础设置删除“翻译目标”和“文本排版”。这两项只在翻译工作台中调整，避免设置页与当前弹窗出现两个互相覆盖的入口。

现有目标语言和排版偏好继续作为兼容迁移输入，但升级后由翻译工作台维护最后一次选择。新安装默认使用 `自动识别 + 智能排版`。

### 2.2 翻译工作台

原文和译文编辑区继续保留编辑、复制和朗读能力，并新增明确的手动 AI 操作：

- 原文：`智能排版`、`智能润色`；
- 译文：`智能排版`、`智能润色`。

初次翻译和“重新翻译”都只执行 Azure Text Translation，不根据当前文本处理模式自动调用 GPT。用户主动点击原文的“智能润色”时，才允许改变原文表达。

翻译工作台底部是目标语言和文本处理的唯一入口：

- `目标语言`：`自动识别（中文 → 英语，其他 → 简体中文）`，或直接选择具体目标语言；
- `文本处理`：`严格保留`、`智能排版`、`智能润色`。

弹窗打开时使用上一次选择；选择变化立即保存为下次默认，但不因一次下拉选择自动产生新的云端费用。“重新翻译”使用当前目标语言发起快速基础翻译，不调用 GPT。初次打开新选区时按已保存目标语言自动翻译。

`严格保留`不显示一键 AI 按钮。`智能排版`显示“一键智能排版”，用户点击后用一次 Azure GPT 请求同时整理原文与译文结构且不修改文字。`智能润色`显示“一键智能润色”，用户点击后原文只排版，译文在排版基础上润色。两个一键操作都必须同时捕获当前两侧文本，成功时原子更新两侧。

原文编辑区必须以捕获到的原始选区结构为基线。源应用已经提供的段落、空行、项目符号、编号、缩进和签名边界不得在进入工作台前被本地格式化器合并。对于已有标准结构的邮件，右侧原文应保持与源邮件相同的阅读层级；译文使用同一组结构边界逐块翻译和重组。

按钮在请求期间显示处理中状态并防止重复提交，但另一侧编辑、复制和停止朗读仍可用。AI 成功前保留当前编辑内容，失败、取消、响应过期或校验不通过时不得覆盖编辑器。

### 2.3 结构化报告视觉

用户确认采用“结构化报告”视觉方案。Azure GPT 负责识别语义区块，Glint 使用固定的 macOS 原生富文本样式渲染；模型不得自行决定字体、字号、颜色或任意 HTML。

支持的视觉区块包括：

- 问候语；
- 普通正文；
- 重点清单；
- 标题或小节；
- 引用或说明；
- 代码与简单表格；
- 邮件签名。

视觉规则：

- 正文使用克制的系统字体、约 1.55 倍阅读行距和明确段间距；
- 重点清单使用浅色背景、左侧强调色条、稳定缩进和较大的项目间距；
- 标题与小节使用半粗体和轻量颜色层级，不使用夸张大字号；
- 案件号、金额、日期等不可变信息可使用半粗体提升扫描效率，但不得改变内容；
- 签名使用顶部细分隔线和次级文字颜色；
- 原文和译文使用相同区块顺序与对应视觉层级；
- 强调区的“重点清单”等名称属于 Glint 界面装饰，不写入正文，也不进入纯文本复制结果。

编辑器升级为可编辑富文本。用户继续直接修改文字；未修改区块保留样式，新增普通文本使用正文样式。复制纯文本时保留段落、列表和原始文字，复制 RTF 时同时保留当前视觉层级。

### 2.4 状态提示

工作台使用可理解的阶段提示：

- `正在翻译…`
- `正在智能排版…`
- `翻译完成`
- `正在智能排版原文与译文…`
- `正在智能润色原文与译文…`
- `智能排版完成`
- `智能润色完成`
- `AI 处理结果可能改动受保护内容，已保留处理前内容`

提示不得包含 Key、完整正文或 Endpoint 查询参数。

## 3. 翻译与 AI 数据流

### 3.1 基础翻译与按需处理

所有模式首先保留一份未经排版器处理的 `rawSourceText`。结构提取器从原始选区识别并保存段落、空行、Unicode 项目符号、编号列表、引用、表格、代码与签名边界；后续本地处理、Translator 和 GPT 均不得提前丢弃这些边界。

`初次翻译 / 重新翻译`：

```text
选中文字
→ 最低限度规范化
→ Azure Translator
→ 显示原文与译文
```

`一键智能排版`：

```text
当前原文 + 当前 Translator 译文
→ 一次 Azure GPT 请求
→ 返回 source_blocks + translation_blocks
→ 忠实性校验
→ 原生富文本渲染原文与译文
```

`一键智能润色`：

```text
当前原文 + 当前 Translator 译文
→ 一次 Azure GPT 请求
→ 返回 source_blocks + translation_blocks
→ 忠实性与事实保护校验
→ 原生富文本渲染原文与译文
```

Translator 仍是唯一默认翻译引擎。GPT 不替代 Translator，也不决定目标语言；只有用户点击一键或单侧 AI 按钮时才发起请求。

Translator 按结构区块翻译并原位重组。一个源项目符号对应一个译文项目符号，一个源段落对应一个译文段落；已有空行继续作为段落分隔。只有源应用确实未提供可靠边界时，智能排版才允许根据句法恢复缺失换行。

### 3.2 GPT 请求协议

复用已配置的 Azure OpenAI `/openai/v1/chat/completions` 和部署名称。一键处理使用一次请求同时提交当前原文与 Translator 译文。系统提示词要求模型先保留所有文字和事实，再识别问候、正文、重点清单、标题、引用、代码、表格和签名。模型只返回严格 JSON，例如：

```json
{
  "source_blocks": [
    { "type": "salutation", "text": "Hi Jhovine," },
    { "type": "paragraph", "text": "..." },
    { "type": "key_points", "items": ["...", "..."] },
    { "type": "signature", "text": "Best regards,\nYa Chen" }
  ],
  "translation_blocks": [
    { "type": "salutation", "text": "你好，Jhovine：" },
    { "type": "paragraph", "text": "..." },
    { "type": "key_points", "items": ["...", "..."] },
    { "type": "signature", "text": "此致\nYa Chen" }
  ]
}
```

智能排版模式下，两个区块数组都只能调整结构和空白。智能润色模式下，`source_blocks` 仍只能排版，`translation_blocks` 允许润色。请求采用低随机性设置，不请求流式输出，不记录正文。

模型只能选择已定义区块类型，不能返回颜色、字体、CSS、HTML 或任意视觉参数。Glint 将区块重组为规范纯文本执行忠实性和事实保护校验，校验通过后再由固定渲染器生成富文本。

手动处理只提交当前编辑区文本，并返回该侧的结构化区块数组。请求开始时捕获编辑器版本；如果用户在等待期间修改了文本，晚到响应必须丢弃。

### 3.3 智能排版边界

智能排版遵循以下优先级：

1. 保留源应用已经提供的正确结构；
2. 修复缺失的空格、换行和列表边界；
3. 无法可靠判断时保持原样，不主动合并。

智能排版仅允许：

- 插入、删除或调整空格与换行；
- 使用现有标记恢复标题、段落、列表、引用、代码、简单表格和邮件签名结构；
- 修复标点后缺少空格造成的单词粘连。

列表识别必须覆盖常见 Unicode 符号，包括 `•`、`◦`、`▪`、`‣`、`–`，以及现有的 `-`、`*`、`+` 和数字编号。列表行必须作为独立区块，不得与前后段落连接。

智能排版不得新增、删除、改写或重排任何非空白字符。校验时分别移除输入和输出中的 Unicode 空白字符，两者剩余字符序列必须完全一致。校验失败即拒绝 GPT 输出。

### 3.4 智能润色边界

智能润色允许改善：

- 语法与拼写；
- 用词和句式；
- 语气、流畅度和专业程度；
- 段落、标题、列表与签名结构。

智能润色不得虚构、删除或修改以下事实与不可变信息：

- 人名、组织名和资源名；
- 案件号、订单号、工单号和其他标识符；
- 数字、金额、百分比、日期与时间；
- URL、邮箱、IP、路径、变量名和代码；
- 原有列表项目表达的事实数量与顺序。

请求前提取上述保护项，请求后验证所有保护项仍存在且出现次数不减少。正文为空、JSON 无法解析、字段缺失或保护项校验失败时拒绝输出。润色属于语言改写，无法用字符完全相等校验，因此界面必须保留用户执行前内容，失败时原样恢复。

## 4. 回退与成本控制

- Azure GPT 未配置时，默认 Translator 翻译不得被阻断；只有用户点击 AI 按钮时提示配置不完整；
- GPT 网络错误、非 2xx、响应为空、JSON 错误或校验失败时，不用失败内容覆盖编辑器；
- 初次翻译和重新翻译不增加 GPT 请求；
- 一键或单侧智能排版 / 润色每次用户点击增加一次 GPT 请求（长文本可按预算分批）；
- 长文本超过模型预算时按稳定段落边界分批，每批独立校验，任一批失败则整次 AI 结果不落入编辑器；
- 最近结果只在 Translator 成功并完成本次允许的处理后写入；手动 AI 成功后更新同一条记录，不新增重复记录。

## 5. Azure Speech 设置重构

### 5.1 默认表单

Speech 设置组只保留：

- `Endpoint`：直接粘贴 Azure Portal 展示的终结点；
- `API Key`：安全输入，不写日志；
- `测试连接`：使用固定短文本发起最小真实合成请求，不包含用户正文，也不自动保存。

Endpoint 同时接受以下两种格式：

```text
https://<region>.api.cognitive.microsoft.com/
https://<region>.tts.speech.microsoft.com/cognitiveservices/v1
```

当用户粘贴 Portal 通用终结点时，Glint 自动提取 `<region>` 并生成实际请求地址：

```text
https://<region>.tts.speech.microsoft.com/cognitiveservices/v1
```

Glint 不显示 Region 或 Voice 字段。Region 从 Endpoint 自动识别；Voice 始终根据当前朗读内容的语言代码自动选择 Neural Voice。用户不需要知道或填写声音名称。

### 5.2 旧配置迁移

配置模型保持向后兼容：

- 旧 Endpoint 为标准 TTS 地址时继续使用；
- 旧 Endpoint 是 Portal 通用终结点时，运行时自动生成标准 TTS 地址；
- 旧 Voice 无论是 `auto`、合法 Voice、误填 Region 或其他无效值，升级后统一改为自动匹配语言；
- 迁移不得修改或输出 API Key；
- 保存新配置后只持久化用户输入的 Endpoint 和 API Key，Region 与 Voice 均不作为用户设置项。

### 5.3 测试连接与错误信息

测试连接必须分阶段校验并返回具体信息：

- `请填写 Speech Endpoint`
- `Speech Endpoint 格式不正确，无法识别 Azure 区域`
- `请填写 Speech API Key`
- `Speech Key 无效或资源区域不匹配`
- `自动选择的语音在当前区域不可用`
- `网络错误：…`
- `✓ Azure Speech 连接成功`

客户端字段校验失败时不得发送网络请求。HTTP 和网络错误继续通过脱敏器处理。

## 6. 组件边界

- `TranslationAIService`：构造排版/润色请求、解析严格 JSON、处理分批与错误；
- `TranslationContentValidator`：智能排版字符忠实校验、润色保护项提取与校验；
- `TranslationBlockRenderer`：将已校验的结构化区块转换为固定的“结构化报告”富文本样式和规范纯文本；
- `TranslationService`：负责 Translator 请求、单侧 AI 处理和双侧一键 AI 处理，三条链路不隐式串联；
- `TranslationWorkbench`：保存当前编辑状态、重译代际、单侧 AI 代际、双侧 AI 代际和最近结果更新；
- `AzureSpeechConfig`：保存 Endpoint 和 Key，兼容旧配置，从 Endpoint 解析 Region，生成运行时 TTS 地址并自动选择 Voice；
- `Settings`：只显示 Speech Endpoint、API Key 和精确连接探测结果。

各组件通过明确输入输出协作；UI 不自行拼接 GPT JSON 或 Speech Endpoint，网络服务不直接修改编辑器状态。

## 7. 隐私与安全

- Key 只保存在现有本机配置中，不写入日志、测试、设计文档或错误提示；
- GPT 请求包含用户主动翻译或主动润色的正文，这是功能必要行为；界面不额外上传剪贴板历史；
- Translator、GPT 和 Speech 错误必须脱敏 Key、Endpoint 查询参数和正文；
- 音频继续只保存在内存中；
- 测试全部使用虚构 Endpoint、Key 与正文；
- UI smoke 必须设置独立 `GLINT_CONFIG_DIR`，不得加载用户真实配置。

## 8. 测试与验收

按照仓库 TDD 约束，业务实现前由全新上下文的独立测试 Agent 编写黑盒契约测试并先确认失败。至少覆盖：

- 三种默认文本处理模式的迁移、保存与路由；
- 智能排版请求、严格 JSON 解析、字符忠实校验与失败回退；
- 结构化区块白名单、未知类型拒绝、模型视觉参数拒绝和原生富文本渲染；
- 重点清单强调区、正文层级、签名分隔以及原文与译文视觉对应；
- 纯文本复制不包含界面装饰标签，RTF 复制保留结构化报告样式；
- 已有标准邮件段落、连续 Unicode 项目符号、空行和签名在原文中保持，译文结构逐块对应；
- `•`、`◦`、`▪`、`‣`、`–` 列表不会被拼接到前后段落；
- 智能润色保护项提取、计数校验、空响应与失败不覆盖；
- 默认翻译在三种文本处理模式下都不调用 GPT；
- 一键按钮随智能排版 / 润色模式改变，严格保留时隐藏或禁用；
- 双侧一键处理原子更新，任一侧编辑或开始重译后拒绝晚到响应；
- 请求期间用户编辑导致晚到响应失效；
- Portal 通用 Endpoint 自动生成 TTS Endpoint；
- Portal 通用 Endpoint、标准 TTS Endpoint 与旧 Voice 字段的兼容迁移；
- Voice 按语言自动匹配，设置页不出现 Region 或 Voice；
- Speech 真实探测请求不含用户正文；
- Translator、提问、截图、快捷键、最近结果、复制、朗读和既有配置不回归；
- Universal Binary、固定签名、隔离 UI smoke 和 `/Applications/Glint.app` 安装通过。

提交前执行独立只读终审，必须达到 `APPROVE` 且 `P0=0 / P1=0 / P2=0`。发布使用功能分支、GitHub PR 和 merge commit 合并 `main`，不 squash、不 rebase，并保留功能分支。

## 9. 不在本版本范围内

- 不让 GPT 取代 Azure Translator；
- 不恢复源应用中的字体、颜色、图片、分页或复杂 HTML/CSS；
- 不提供云端历史同步或持久化会话；
- 不动态下载 Azure 全量声音目录；
- 不改变快捷键、截图、提问和最近 10 条仅内存历史的现有产品规则。
